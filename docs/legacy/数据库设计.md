# LinkGame 数据库设计

最后修改日期：`2026-09-08`

## 身份与会话

```text
players
├── player_identities(provider, provider_uid)
└── player_sessions(token_hash, expires_at, revoked_at)
```

同一平台身份有数据库唯一键。新玩家、身份和 session 在同一事务创建。明文 Token 只在登录
成功响应出现一次，库中保存 32 字节 SHA-256。

## 匿名启动诊断（2026-09-08）

`startup_diagnostic_events` 由 migration `000037` 创建，以唯一 `event_id` 幂等保存登录前阶段事件，并按 `received_at + stage`、`launch_id`、客户端/系统/TikTok/SDK 版本建立查询索引。表中不保存平台 code、Token、OpenID、账号或玩家 ID。

## 总排行榜与公开资料（2026-09-08）

`player_public_profiles` 由 migration `000038` 创建，使用自增 `player_number` 作为稳定、唯一、不可变的公开编号；`player_id` 保持唯一外键。表内只保存授权状态、清洗后的 TikTok 昵称、合法 HTTPS 头像和资料更新时间，不保存 access token、refresh token 或 OpenID。migration `000039` 按玩家主键顺序为历史玩家一次性回填资料行；以后登录创建玩家时同步确保该行存在。

`player_saves.reached_level_at` 由 migration `000040` 增加，并建立 `(level DESC, reached_level_at ASC, player_id ASC)` 索引；migration `000041` 使用旧存档 `updated_at` 回填历史记录。只有提交的 `level` 真实前进时才更新到达时间，同级存档同步不会改变同关玩家顺序。Top N 与当前玩家名次在同一个 `REPEATABLE READ` 只读事务中使用窗口函数计算。

`player_saves` 是当前权威快照；mutation 表是幂等账本。每次 PUT 先锁存档、校验 revision，
再写账本和余额，最后统一加 revision；任何一步失败整笔回滚。

主题 0 的 27 片视为默认拥有，不产生 27 条冗余记录。其余碎片按
`player_id + theme_id + fragment_index` 唯一。当前普通通关只允许普通主题碎片；限定主题留给
后续可信活动/运营发放路径。

`player_daily_gifts` 的 V2 记录以 `player_id + Asia/Tokyo day_key + reward_version` 唯一，
首次查询即持久化基础与追加两组“刷新道具 + 不同限定主题碎片”。免费领取基础奖励与激励广告
追加领取分别在事务内写资产流水、主题库存、领取时间和 revision。V1 历史记录保留用于审计，
不会在升级时删除或改写。

`player_ad_sessions` 由服务端签发，按玩家、业务位和业务键唯一；记录 10 分钟有效期、领取状态、
幂等请求号、同一 SDK `ad_attempt_id` 和首次响应。已经领取的业务键不能重新签发。

`player_tiktok_mission_claims` 以 `player_id + mission_key` 唯一，当前保存添加桌面与 Profile
侧边栏两项任务。平台固定 mutation、任务完成状态、库存/主题碎片和 revision 在同一事务提交；
`000020` 会把添加桌面的历史 coin/hint/shuffle 及已存在的新固定流水回填为已领取，`000021` 对
Profile 再访任务执行对应回填，防止版本切换重复发奖。

`player_daily_challenge_states` 保存绝对挑战进度、东京自然日完成次数、布尔广告资格和活动轮次；
`daily_challenge_attempts` 保存服务端生成的关卡、模式、固定奖励快照、start/complete 幂等键及完整首次
结算响应；跨东京零点的未完成轮次标为 `expired` 并保留审计，新日可以从同一绝对关卡重新创建免费轮。
开始挑战不消费广告资格，只有同一事务内成功发奖才完成轮次并消费资格。每日挑战碎片或
120 星星通过既有 mutation 账本入账，库存、revision、轮次和资格要么全部提交，要么全部回滚。

`player_season_months` 固化玩家自然月的 `config_version / config_id / state_version`，并保存 0～5 次
补签余额与最后恢复的东京 `day_key`；跨过一个或多个自然日都只恢复 1 次，不按离线天数追补。
`player_season_days` 保存 1～25 日的通关次数、两项领取时间、最终发奖时间和版本化奖励快照。
`player_season_clear_events` 以玩家加 request/completion 双唯一键去重普通关与每日挑战成功结算；
`player_season_task_claims` 保存任务领取的参数和完整首次响应。第二项任务完成最终发奖时，赛季状态、
道具、主题集合、既有 mutation 账本和 save revision 在同一事务提交。GM 只读接口可按公开玩家 ID
查询当月状态、事件、请求与奖励流水，不提供绕过事务的补发入口。`player_season_makeup_claims` 额外
记录目标日、`session_id / ad_attempt_id / business_key`、奖励快照和到账后的 save revision；补签
扣次数、历史日标记、奖励入账、广告会话核销和审计写入同一事务。

## 游戏与广告统计

```text
analytics_events              原始幂等事件
analytics_player_stats        玩家累计快照
analytics_daily_user_stats    每日汇总
analytics_funnel_events       每玩家/关卡/步骤首次到达
```

报表日期以服务端接收时间和 `ANALYTICS_TIMEZONE` 为准。客户端时间只用于顺序排查。
统计失败不影响存档和玩法事务。

`000022`（2026-08-31，已随服务端 `20260831035656` 发布）为广告原始事件增加客户端版本、平台、`ad_attempt_id`、失败阶段、
TikTok 子错误码、关闭结果、阶段耗时和预热标记。GM 按尝试 ID 去重计算请求、加载、展示、完播与
奖励核销漏斗；TikTok 后台收入、eCPM 和计费曝光仍是财务权威。

## 迁移顺序

1. 在本地或隔离库执行 `go run ./cmd/migrate`。
2. 对新号、重复登录、重复 mutation、负库存、revision 冲突和统计幂等做冒烟。
3. 正式环境只执行 up migration；不得修改已经执行过的 SQL。
4. 先发布兼容服务端，再接客户端云同步。
