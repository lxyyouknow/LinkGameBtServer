## 4. 配置 SSH 私钥

原生 Windows 工具可以把私钥放到 `C:\Users\<Windows用户名>\.ssh\linkgame.key`，并在
`.release.env` 的 `RELEASE_SSH_KEY` 填这个绝对路径。`.pub` 公钥不是登录私钥，不能填入。

如果选择 WSL，则按下面方式复制并收紧权限：

假设 lxy 把私钥发到了 Windows 下载目录。在 WSL 中把它复制到 Linux 用户目录，并收紧
权限；不要让发布脚本直接读取 Windows 下载目录中的原件。

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
cp /mnt/c/Users/<Windows用户名>/Downloads/linkgame@18.183.189.2.key \
  ~/.ssh/linkgame@18.183.189.2.key
chmod 600 ~/.ssh/linkgame@18.183.189.2.key
```

先只测试 SSH 登录：

```bash
ssh -i ~/.ssh/linkgame@18.183.189.2.key \
  -o IdentitiesOnly=yes \
  linkgame@18.183.189.2
```

首次连接应核对主机指纹后再接受。若出现 `bad permissions`，检查私钥是否位于 WSL 的
`~/.ssh` 且权限为 `600`。`.pub` 公钥不是登录参数，不要把它填到 `RELEASE_SSH_KEY`。

在服务端仓库根目录执行：

```bash

```

编辑 `.release.env`，内容应类似下面这样。原生 Windows 使用 `C:\...` 私钥路径；WSL 使用
`/home/...` 路径：

```dotenv
RELEASE_SSH_HOST=18.183.189.2
RELEASE_SSH_USER=linkgame
RELEASE_SSH_KEY=/home/<WSL用户名>/.ssh/linkgame@18.183.189.2.key
RELEASE_REMOTE_ROOT=/home/linkgame/linkgame-server
RELEASE_SYSTEMD_SERVICE=linkgame.service
RELEASE_HEALTH_BASE_URL=http://127.0.0.1:23020
```

`.release.env` 已被 `.gitignore` 忽略。这里不需要数据库密码，也不需要 AWS AK/SK；发布
脚本会在远端读取已有的 `/home/linkgame/linkgame-server/shared/app.env`。

首次先做只构建测试，不更新线上：

```bash
./scripts/release-production.sh --build-only
```

原生 Windows 对应命令是：

```powershell
.\scripts\release-production-windows.ps1 --build-only
```

它会依次执行 `go test ./...`、`go vet ./...`，再交叉编译 Linux amd64 发布包。确认通过后，

```bash

```

原生 Windows 可直接双击 `一键发布服务端-Windows.bat`。两套脚本都会要求手工输入

脚本要求手工输入 `RELEASE`，然后按以下顺序执行：上传版本包、运行正式库 up migration、

`--yes`。

## 6. 数据库密码怎么用

正式服务的数据库 DSN 已保存在服务器：

```text
/home/linkgame/linkgame-server/shared/app.env
```

日常发版不要重建、覆盖或下载这个文件。只有轮换密码或修改运行参数时，才通过 SSH 登录
服务器后编辑。DSN 格式参考仓库中的 `deploy/systemd/app.env.example`：

```dotenv
MYSQL_DSN='linkgame:<数据库密码>@tcp(database-2.c9ie8y6eckdj.ap-northeast-1.rds.amazonaws.com:3306)/linkgame?charset=utf8mb4&parseTime=true&loc=UTC&time_zone=%27%2B00%3A00%27&timeout=5s&readTimeout=5s&writeTimeout=5s'
```

如果密码含有 DSN 保留字符，应先按 MySQL DSN 规则转义，不能直接拼接。改完配置后先检查
文件权限，再重启和验收：

```bash
chmod 600 /home/linkgame/linkgame-server/shared/app.env
systemctl --user restart linkgame.service
systemctl --user status linkgame.service --no-pager
curl --fail http://127.0.0.1:23020/health/ready
```

### 从 Windows 工作机连接正式库

RDS 不应开放公网。先在 WSL 中建立 SSH 本地转发，并保持该终端窗口开启：

```bash
ssh -i ~/.ssh/linkgame@18.183.189.2.key \
  -o IdentitiesOnly=yes \
  -N \
  -L 133123:database-2.c9ie8y6eckdj.ap-northeast-1.rds.amazonaws.com:3306 \
  linkgame@18.183.189.2
```

然后在 DBeaver、DataGrip 或 MySQL 客户端中填写：

```text
Host: 127.0.0.1
Port: 133123
Database: linkgame
User: linkgame
Password: lxy 单独发来的数据库密码
```

不要把正式数据库密码写入仓库 `.env`，也不要为了方便把 RDS 安全组开放到公网。

```dotenv
ANALYTICS_GM_USERS=lxy:<密码>,wlr:<密码>,xy:<密码>
```

当前三个账号的密码由 lxy 单独发送。修改后需重启 `linkgame.service`。不要在前端代码、
仓库文档或客户端构建包中保存 GM 密码。

## 8. AWS AK/SK 怎么用

AWS 凭据只用于客户端 Web 包上传，不参与 Go 服务端构建、数据库 migration 或服务器重启。
在 Windows PowerShell 安装 AWS CLI 后，创建独立 profile：

```powershell
aws configure --profile linkgame-release
```

按提示输入 lxy 单独发送的 Access Key、Secret Key，并把默认区域设置为
`ap-northeast-1`。AWS CLI 会把凭据保存在当前 Windows 用户目录的 AWS 凭据文件中，
不要设置为项目环境文件，更不要提交。可用下面命令只读验证身份：

```powershell
aws sts get-caller-identity --profile linkgame-release
```

客户端资源目标为：

```text
S3 bucket: jptt-588458182172-ap-northeast-1-an
S3 prefix: linkgame/
CDN: https://jptt-aws.bffbond.com/linkgame/
固定游戏入口: https://jptt-aws.bffbond.com/linkgame/game.html
```

客户端发版应优先使用客户端仓库内的发布工具，不要手工执行带 `--delete` 的 S3 同步命令。
发布服务端的同事如果不负责客户端发版，可以不配置 AWS 凭据。

## 9. 开发与数据库迁移规则

修改 Go 代码后至少执行：

```bash
gofmt -w $(rg --files -g '*.go')
go test ./...
go vet ./...
```

数据库 migration 必须遵守：

1. 已进入任何环境的 migration 禁止修改，只能新增更大编号的 migration。
2. 正式环境只执行 up migration，不执行 down，不清空玩家或统计数据。
3. 先在本地或隔离库验证，再随服务端发布脚本执行正式 migration。
4. 金币、道具、主题碎片继续使用幂等 mutation，不能改成客户端直接上传余额。
5. 云存档继续使用 revision 乐观锁，不能用 `max(local, cloud)` 合并经济资产。
6. 当前客户端的音乐、音效和震动开关只存在设备本地，不以数据库字段为权威。

交接提交必须包含 `000013_set_initial_prop_counts_zero` 及其配套 Go 代码和测试；否则新玩家
初始道具可能回到旧行为。正式环境已知执行到 `000041`，接手后禁止修改这些已发布 migration。

源码包含每日礼包与广告 migration `000014`～`000018`、已发布的 `000019`～`000021`、
2026-08-31 已发布的广告统计 migration `000022`，以及已随服务端 `20260831143419` 发布的每日挑战 migration `000023`～`000025`：
`000019` 新增 `player_tiktok_mission_claims`，`000020`～`000021` 分别回填旧版添加桌面/Profile
流水，云存档返回 `claimedTikTokMissions`；`000022` 扩展广告请求、加载、展示、关闭/完播、错误阶段与
奖励核销漏斗；`000023`～`000025` 创建每日挑战权威状态、固定奖励轮次并允许
`daily_challenge_replay` 一次性广告会话。`000026`～`000029` 已随 `20260901134809` 发布自然月赛季；
2026-09-02 新增的 `000030`～`000032` 已随 `20260902041826` 发布，保存补签余额/恢复日、补签审计以及
`season_makeup + ad_attempt_id` 广告约束；`000033`～`000036` 拆分主线开始统计及历史回填，`000037` 新增匿名启动诊断，`000038`～`000041` 新增总榜公开资料、历史玩家回填、稳定到达时间和排序索引。补签扣次数、历史日固定奖励、save revision、广告核销与审计必须同事务。后续发布顺序仍为
服务端 migration → 服务端健康检查/补签冒烟 → Web/TikTok 客户端包。

## 10. 发布前后检查清单

发布前：

- `git status --short`，确认没有密钥、`.env`、`.release.env` 或无关改动被纳入提交。
- `go test ./...` 和 `go vet ./...` 通过。
- 新 migration 编号连续，且没有修改已经发布过的 SQL。
- 先执行 `--build-only`，确认能生成 Linux amd64 包。
- 明确本次是否获得 lxy 的正式发布授权。

发布后：

```bash
curl --fail https://linkgame.bffbond.com/health/live
```

领取、最终原子发奖、每日挑战只推进一次和 GM 玩家审计；统计接口失败不能阻塞正常玩法和云存档。

## 11. 回退原则

发布脚本会保留 `/home/linkgame/linkgame-server/releases/<version>`。服务程序需要回退时，
先确认目标旧版本与已经执行的数据库 migration 仍然兼容，再切换 `current` 软链并重启。
数据库 migration 不随程序回退自动执行 down。

```bash
readlink -f /home/linkgame/linkgame-server/current
ls -1 /home/linkgame/linkgame-server/releases
ln -sfn /home/linkgame/linkgame-server/releases/<确认过的旧版本> \
  /home/linkgame/linkgame-server/current
systemctl --user restart linkgame.service
curl --fail http://127.0.0.1:23020/health/ready
```

若不能确认旧二进制是否兼容当前数据库结构，不要直接回退，应先联系 lxy 并做向前修复。
